# Taste
- Prefers consistent card sizing across sections of the same page: on the homepage, sections like Trending Venues, Go Local, and Influencers should match the Upcoming Events card width on desktop instead of scaling larger. Confidence: 0.8
- Prefers content and feature chips to be visually centered — within wide page containers, inside card boxes, and in wrapped chip rows — rather than hugging the left edge; left-aligned content is explicitly said to "not look good" (asked that the "What's included" heading, body copy, and feature chips all be centrally aligned). Confidence: 0.7
- Prefers call-to-action content (heading, description, and action button) to be centered within its card on all screen sizes — a CTA button sitting left-aligned on desktop (e.g., via `md:justify-start` / `md:text-left` overrides) is a bug to fix, not a deliberate layout choice. Confidence: 0.6
- Maintains separate components for mobile vs. desktop views of the same UI, rather than one fully responsive component; prefers changes to desktop layout to target the desktop-specific components. Confidence: 0.6
- Prefers scroll-aware mobile headers: the header should hide/shrink when scrolling down and expand/reappear when scrolling up, rather than staying fixed at a constant height. Confidence: 0.8
- Prefers the compact/shrunk mobile header to still show all core elements — brand string, logo icon, and action icon buttons (e.g., cart + hamburger). Action buttons should stay visible even when their state is empty (e.g., cart icon always rendered rather than gated on `totalItems > 0`). Confidence: 0.7
- When a mobile header shrinks to a smaller height, the logo icon and brand text should scale down proportionally (e.g., 30% smaller) to match the reduced height, with a smooth transition, while desktop keeps full size. Confidence: 0.7
- Wants responsive/layout fixes to apply to all breakpoints: when reporting a mobile view problem, expects the desktop view to also be reviewed and fixed for any discrepancies, so both views are polished and consistent. Confidence: 0.6
- Wants performance/bug issues diagnosed to root cause before fixing, rather than patching symptoms (explicitly asked to "find out the root cause and then fix"; also asks "What is the issue? Can you check?" when reporting UI bugs). Confidence: 0.85
- Expects horizontally scrollable carousels on the same page to have consistent first-card alignment: the first card should sit centered/inline with the same left inset across sections (e.g., upcoming events vs. trending menus on mobile), and any section whose first card appears off-center relative to its siblings is a bug to fix. Confidence: 0.8
- Cares about scroll performance and fluidity — fast scrolling on any page should not glitch or jank; performance issues are taken seriously and expected to be fixed properly (e.g., eliminating frame-budget hogs that saturate the main thread, avoiding simultaneous entrance animations on fast scroll). Confidence: 0.8
- Prefers scroll-based lazy loading: heavy page sections should be mounted/rendered on demand as they approach the viewport (rather than all at once up front), with lazy-loaded images, so scrolling from top to bottom is smoother. Confidence: 0.7
- Prefers filter UIs (category/date filters) to have no default "All" option: nothing is selected by default (all results shown), and a filter is only shown once the user selects it; removing a selection returns to the unfiltered state. Confidence: 0.8
- When a filter is toggleable (clicking the active option deselects it), expects all filter rows sharing the same behavior (e.g., date tabs and category pills) to behave consistently. Confidence: 0.6
- Expects filter controls in the same context/section to share one consistent visual design: on the homepage "Upcoming" section, the event date filter should be styled exactly like the other category filters on the page, not as a bespoke/different-looking control. Re-confirmed with the explicit scope "design only" — when the issue is a visual inconsistency, only the styling should change, not the filter's behavior/functionality. Confidence: 0.8
- Wants text/content sections to have proper horizontal padding so content never runs edge-to-edge against the viewport; text that touches the screen edges is considered a bug to fix. Confidence: 0.7
- Prefers static cards and chips: does not want scroll-triggered entrance animations (e.g., `whileInView`/`motion.div` fade-and-slide) on cards when scrolling down a page — content should simply be visible without scroll choreography. Confidence: 0.8
- Cares about pill/chip shape consistency and symmetry: pill-shaped chips should render as a clean single line with uniform, symmetric padding (e.g., `inline-flex items-center` + `leading-none`), and inconsistent/squarish (e.g., `rounded-xl`) or unevenly sized chips are considered sloppy. Confidence: 0.7
- Prefers chip rows on mobile to be a single horizontally scrollable snap line (swipeable, `overflow-x-auto` + `snap-x`, no wrapping) rather than wrapping into ragged rows of uneven-width chips; desktop keeps the centered wrap layout. Re-confirmed when explicitly asked to make the "What's included" chip row horizontally scrollable, not wrapped/vertically stacked. Confidence: 0.75
- Prefers repeated card/feature markup across sections to be extracted into one simple shared, reusable component and reused for all the cards (explicitly asked to "create a simple component and reuse all the same component for all the cards"), rather than duplicating per-section markup. Confidence: 0.8
- Prefers duplicated page sections (e.g., the same Organizer CTA section copy-pasted into the home page and the About page, or split across two separate components) to be consolidated into one single shared component and reused everywhere — explicitly asked "make it single component and use it in about section as well" after noticing the same section existed in two places via two different components. Per-page inline copies of the same section are a problem to eliminate, and removing unused/dead duplicate components is expected as part of the consolidation. Confidence: 0.85
- On mobile, prefers feature/info cards laid out as a horizontal row with the icon on the left and title on top with the description/subtitle below it on the right; on desktop, where the card switches to a centered vertical column layout, the icon must also be centered within the card (e.g., `md:mx-auto`) — a left-pinned icon in the desktop column view is a bug to fix, not a deliberate layout. Confidence: 0.7
- Pays attention to the visual scale of large decorative elements (e.g., big circles in a section) and expects them to be reduced/scaled down on mobile so they don't overwhelm the small viewport, while desktop can keep the larger size. Confidence: 0.7
- Wants UI borders/outlines to be clearly visible in both light and dark themes: a border token so dark that it disappears against the dark background is considered a bug — prefers a light grey border that reads clearly in dark mode too, applied everywhere borders exist (explicitly asked to "add a light grey border everywhere where we have the border in the white theme" because the border "is not seen" in the dark theme). Confidence: 0.8
- Prefers theme/styling fixes to be applied site-wide via shared tokens ("everywhere where we have the border") rather than patching individual components or sections, so the whole app stays visually consistent. Confidence: 0.6
- On mobile, prefers multi-card sections (e.g., plan selection cards, media/video showcases) to be horizontally scrollable swipeable rows with fixed card widths instead of stacking vertically down the page; desktop keeps the multi-column grid. Applies as a general rule to any section listing multiple cards/items (explicitly asked that "Select your plan" and marketing showcase cards "should be horizontally scrollable, not stacked"). Confidence: 0.8
- Explicitly does not want the category filter section visible on the home page's desktop view: category filter controls "should not be visible" — "for desktop view" the filter pills bar must be hidden on desktop (`md:hidden`), kept as a mobile-only element; their appearance on desktop is treated as a bug to remove. Confidence: 0.8
- Expresses sharp frustration ("God dang stop you") when unwanted/unrequested UI keeps appearing in the app; expects such elements to be decisively removed and not re-introduced. Confidence: 0.5
- Dislikes decorative data-visualization widgets (animated progress bars, graphs, stat panels) on marketing/promo pages — explicitly asked to "remove the graphs" from a marketing section because they "do not look good"; prefers clean, balanced card-tile layouts (icon box + title + description) instead. Confidence: 0.6
- Prefers detail pop-ups/modals for similar content types (e.g., venue vs. partner/creator detail views) to be visually and behaviorally identical — explicitly asked to "make one change in one component and keep it consistent across both" after spotting that one pop-up was vertically long and the other horizontally wide; expects a single shared modal component to drive the layout rather than per-section implementations. Confidence: 0.8
- Accepts the mobile bottom-sheet pattern (modal sliding up from the bottom) as the right mobile treatment for detail pop-ups, but expects that variant to be styled/polished too — "opening from the bottom is all right, but it is not looking good." Confidence: 0.6
- Prefers images inside detail pop-ups/modals to render at a consistent standard aspect ratio (Instagram-style 4:5 portrait) rather than stretching to fill the panel: images should sit in a fixed aspect-ratio container (cropped with `object-cover`), shrunk to fit, so every image displays at the same standard size regardless of its source dimensions — a giant blown-up/stretched image in a modal is a bug to fix (explicitly asked to "shrink the image to the standard size of Instagram, because all the images will be in a 4:5 aspect ratio"). Confidence: 0.85
- Prefers detail pop-ups/modals to have a fixed height and a fixed overall design regardless of content length: long descriptions/subtitles should scroll inside a fixed-height content area (the pop-up must not grow or reshape itself when content expands) — explicitly asked that the pop-up "should be of a fixed height, not of any height" and that a multi-paragraph description "will be scrollable, not the whole pop-up design." Confidence: 0.85
- Prefers long subtitles/descriptions inside modals to be collapsed with a "More" link at the end (expand/collapse toggle) so the initial view stays compact and the layout doesn't jump — "if it is very large, show more at the end." When expanded, the text must not grow the popup: it should scroll inside a predefined fixed max-height area (e.g., `max-h-40 overflow-y-auto`) rather than removing the clamp and growing unbounded. Confidence: 0.8

Please fix them all").
